==================================================
1. CORE ARCHITECTURE PRINCIPLE
==================================================

V1 and V2 are architecture states, not automatically:

V1 = correct
V2 = incorrect

or:

V1 = baseline truth
V2 = proposed truth

The user may upload:

Case A:
V1 = Existing/Baseline
V2 = Proposed/Changed

OR:

Case B:
V1 = Proposed/Changed
V2 = Existing/Baseline

OR:

Case C:
Both are simply two versions that the user wants to compare.

Therefore:

- Preserve the labels V1 and V2.
- Do not interpret "V1" as automatically correct.
- Do not interpret "V2" as automatically correct.
- Comparison must describe structural differences objectively.
- Risk must be calculated independently for each architecture.
- Risk delta must be directional and explicitly state the direction.
- Impact analysis must specify which architecture is being used as the starting state.
- Change Simulator must be available for BOTH V1 and V2.

Example:

V1 risk = 43
V2 risk = 18

Do NOT automatically say:

"V2 is safer because it has lower risk."

Instead say:

"V1 structural risk is 43/100.
V2 structural risk is 18/100.
The modeled structural-risk delta from V1 → V2 is -25 points."

If V2 removed an important component and created broken dependencies, the system must separately report those structural breakages.

A lower aggregate score must NEVER hide or override detected broken dependencies.

==================================================

The Compare page must support:

Example UI:

COMPARE DIRECTION

[ V1 → V2 ]

- evidence context

Example:

V2 → V1:

"PaymentService was added in V1."

Both are correct depending on comparison direction.

Do not duplicate architecture data.

==================================================
3. RISK MUST BE CALCULATED INDEPENDENTLY
==================================================

Calculate:

V1 Risk Score
V2 Risk Score

independently from the actual architecture/risk engine.

Then calculate:

Directional Risk Delta:

Delta(V1 → V2) = Risk(V2) - Risk(V1)

Delta(V2 → V1) = Risk(V1) - Risk(V2)

Example:

V1 = 43
V2 = 18

V1 → V2:

43 → 18
Delta = -25

V2 → V1:

18 → 43
Delta = +25

The underlying architecture risk values remain unchanged.

Only the comparison direction changes.

IMPORTANT:

Do not use "fewer nodes = lower risk" as a general rule.

Removing components can:

- reduce coupling
- reduce complexity
- remove obsolete dependencies

BUT it can also:

- break required dependencies
- remove critical services
- remove databases
- increase failure exposure
- disconnect required callers
- create unresolved references

Therefore the risk engine must consider the actual structural risk factors.

OVERALL STRUCTURAL RISK:
V1 = 43
V2 = 18

STRUCTURAL BREAKAGE:
2 broken required dependencies

Then explain why the aggregate score changed and what critical breakages exist.

Never hide serious dependency breakage behind the aggregate score.
